# 架构设计检查清单

> 从 Embed Agent 架构设计过程中提炼。
> 用于下一次软件架构设计时逐条对照。

---

## 一、出发点

### 1. 先定义本质，再画架构

问自己：这个系统到底在解决什么问题？工程师不用这个系统时，怎么做这件事？

```
Embed Agent:
  本质不是"造 agent"，是"替代工程师盯设备的重复劳动"。
  工程师做的事 → 系统做的事，一一对应。
  如果对应不上 → 架构可能想多了。
```

**检查项：**
- [ ] 用一句话说清楚这个系统解决什么问题
- [ ] 把人工流程列出来，看系统能不能每一步都对应上
- [ ] 列出来系统不做的事（边界）

### 2. 核心价值不是"用了什么技术"

```
Embed Agent:
  核心价值不是"用了 LLM"。
  是 grep 做不了的事——时序分析、跨源关联、因果推断、基线对比、主动采样。
  LLM 是实现手段。
```

**检查项：**
- [ ] 如果去掉 AI/LLM/最新技术，这个系统还有独立价值吗
- [ ] 核心价值能有一句话吗（不是"用了 XX 技术"）

---

## 二、概念定义

### 3. 用通用术语，不生造概念

```
Embed Agent:
  不用 "kernel"、"projection"、"intent arbitration"。
  用 "Runtime"、"View"、"Decision"、"Decision Handler"。
  术语要能让新加入的工程师 5 分钟看懂。
```

**检查项：**
- [ ] 每个概念的名字在业界有先例吗
- [ ] 新工程师第一次读，能不能猜出意思
- [ ] 有没有两个概念指的是同一个东西（同义词）
- [ ] 有没有一个概念指两个不同的东西（多义词）

### 4. 区分"决策"和"执行"

```
Embed Agent 核心区分: Decision ≠ Step。
Decision 是"应该做什么"，Step 是"已经被批准排队的设备动作"。
不分开 → 暂停、打断、忽略规则、补采集全乱。
```

**检查项：**
- [ ] 系统里有没有类似 "decision" 和 "action" 需要分开的概念
- [ ] 如果混在一起，哪些功能会出问题

---

## 三、边界设计

### 5. 组件不做的事，和做的事一样重要

```
Embed Agent:
  每个模块有 "不能做" 清单。
  Tool 不能调 LLM。Agent 不能碰设备。Interface 不能持状态。
```

**检查项：**
- [ ] 每个组件有 "不能做" 列表吗
- [ ] "不能做" 列表里有哪几条是防止系统退化的
- [ ] 有没有禁止交互清单（A→B 的边不允许存在）

### 6. 同步 vs 异步：什么时候走 Event Bus，什么时候直接调

```
Embed Agent:
  直接调用: 调用方需要返回值才能继续（RM→Planner, DH→Observer）
  Event Bus: 广播/持久化/多方订阅（Tool→Observation, RM→RunStarted）

  错误模式: 同步依赖走 Event Bus → 多一层间接，还引入竞态
           异步广播走直接调用 → 紧耦合，不可扩展
```

**检查项：**
- [ ] 每个跨模块调用：调用方需要返回值才能继续吗
- [ ] 需要返回值 → 直接调。不需要 → Event Bus
- [ ] 有没有"需要返回值但走了 Event Bus"的错误路径
- [ ] 有没有"不需要返回值但走了直接调用"的紧耦合

### 7. 生产者-消费者边界

```
Embed Agent:
  Step Queue: RM 生产初始 Step，DH 追加/清空，SE 只消费。
  不能有第四方操作 Step Queue。不能 SE 自己生产 Step。
```

**检查项：**
- [ ] 每个共享状态（队列/Map/缓存）: 谁写、谁读、谁清
- [ ] 有没有"消费者又当生产者"的违规

---

## 四、时序检查

### 8. 所有时序走一遍，找循环依赖

```
Embed Agent 发现的:
  Reply 消费 run_completed → 终态定义成 "Reply 写完后" → 死锁。
  修: RM 直接调 Reply，Reply → result_ready → RM 标记终态。
```

**检查项：**
- [ ] 主流程时序图走一遍
- [ ] 异常路径时序图走一遍（失败、超时、中断）
- [ ] 有没有 A 等 B、B 等 A 的循环
- [ ] 有没有 "先有鸡先有蛋" 的初始化问题

### 9. 检查事件的双重消费

```
Embed Agent 发现的:
  Decision 已通过直接调执行。Observer 又发了 DecisionMade 到 EB。
  DH 订阅 EB 的 DecisionMade → 收到自己刚执行过的 Decision，重复执行。

  修: DecisionMade 只走 Event Bus → Store（持久化），不驱动 DH。
```

**检查项：**
- [ ] 每个 Event: 谁发、谁收、收到后做什么
- [ ] 有没有"已经直接调执行了，又发 Event 导致重复执行"
- [ ] 审计事件和驱动事件是否分开了

### 10. 检查通知的竞态

```
Embed Agent 发现的:
  result_ready 和 run_failed 先后到达 NotificationFilter → 同一 Run 通知两次。
  run_failed 的模板引用 reply.summary → Reply 可能还没写完。
```

**检查项：**
- [ ] 通知/回调的依赖数据在通知触发时一定存在吗
- [ ] 同一个事件会不会触发两条重复通知
- [ ] 通知去重策略有吗

---

## 五、决策设计

### 11. 决策分层

```
Embed Agent:
  第一层: 确定性反射 (毫秒, 不走 LLM)
  第二层: LLM 决策 (秒级, 弱模型)
  第三层: 人覆盖 (最高优先级)

  关键: fatal 事件走第一层，不等 LLM。否则比人盯串口还慢。
```

**检查项：**
- [ ] 系统中的判断: 哪些是确定性、不需要 LLM 的
- [ ] 哪些是不确定、需要 LLM 结合上下文的
- [ ] 人怎么覆盖自动决策
- [ ] 不同层的决策冲突时谁赢

### 12. 模型分层

```
Embed Agent:
  Observer(高频) → 弱模型/快/便宜
  Planner(低频) → 强模型
  Reply(低频) → 强模型

  原则: 频率 × 成本 = 总成本。高频必须便宜。
```

**检查项：**
- [ ] LLM 调用的频率分布是什么
- [ ] 高频的一定要用强模型吗？弱模型够不够
- [ ] debounce / 频率限制有吗

---

## 六、观测设计

### 13. 不要拿全量数据喂 LLM

```
Embed Agent:
  Observer 只看 Signal + 窗口，不看全量 serial.log。
  不是因为 LLM 窗口装不下。是因为人不这样看日志。
  人: grep → 看前后文 → watch 趋势 → 感觉不对才细看。
  系统: 一样的。全量存证据，分层做分析。
```

**检查项：**
- [ ] LLM 的输入是什么？是原始数据还是预处理的信号
- [ ] 如果数据量很大（几百 MB），LLM 怎么消费
- [ ] 有没有"人怎么看 → 系统怎么做"的对应关系

### 14. 观测不是只有 grep

```
Embed Agent 六层:
  单行匹配 → 单源时序 → 跨源关联 → 因果链 → 基线对比 → 主动采样

  grep（单行匹配）很容易做。后面五层才是核心价值。
```

**检查项：**
- [ ] 系统能做的检测，有多少层
- [ ] grep 能做的是第几层。grep 做不了的是哪些层
- [ ] 核心价值在哪几层

---

## 七、状态设计

### 15. 状态机不要简化过度

```
Embed Agent:
  Target 状态不只是 idle/busy/offline。
  还有 preparing、cleaning、dirty、recovery。
  简化过度 → 下次 Run 在脏板子上跑 → 结果不可信。
```

**检查项：**
- [ ] 所有"之间"的状态都有名字吗（准备中、清理中、恢复中）
- [ ] 崩溃或中断后的残留状态有表达吗
- [ ] 状态迁移表完整吗（每个 from→to 都有触发条件）

### 16. 锁的范围

```
Embed Agent 发现的:
  Target 锁只覆盖 running/paused → 补采证据时可能被抢。
  修: 锁覆盖 planning 到 cleaning→idle 全周期。
```

**检查项：**
- [ ] 锁从什么时候获取，什么时候释放
- [ ] 有没有"还在用但已经释放锁"的窗口
- [ ] 调度器跳过逻辑和锁的范围一致吗

---

## 八、配置设计

### 17. 配置一次，反复用

```
Embed Agent:
  人配 Target Profile（串口/ADB/设备特性）一次。
  Agent 每次读配置自己决定怎么做。
  不是每次验证时从头问。
```

**检查项：**
- [ ] 哪些配置是"配一次用很久"的，哪些是"每次都要给"的
- [ ] Agent/LLM 用到的上下文数据和配置是分开的吗
- [ ] 配置可版本控制吗（纯文本/YAML）

### 18. Agent 不直接读配置

```
Embed Agent:
  ContextAssembler 预组装上下文 → Planner/Observer 只收 Context。
  好处: Planner 不依赖 Config 结构。Config 变了不影响 Agent。
```

**检查项：**
- [ ] Agent/LLM 的输入是散落的还是组装好的
- [ ] 如果配置结构变了，Agent 要不要改
- [ ] 测试时能不能 mock 输入

---

## 九、可靠性设计

### 19. 重启后诚实

```
Embed Agent:
  启动时 running 状态但无后续 Event → 不装还在跑，标 failed(crashed)。
  不假装。不确定就标失败。
```

**检查项：**
- [ ] 系统崩溃后重启，怎么判断之前的任务还在不在
- [ ] 会不会"假装还在跑"
- [ ] stale 锁怎么处理

### 20. 自观测

```
Embed Agent 发现的:
  系统盯设备。谁盯系统？
  至少要有: LLM 延迟 p50/p99、fallback 率、磁盘用量、Event 量。
  不然线上出问题只能看日志猜。
```

**检查项：**
- [ ] 系统自己有没有健康指标暴露
- [ ] 关键路径（LLM 调用/Event 处理/磁盘）有没有 metrics

### 21. 并发模型不要留白

```
Embed Agent 发现的:
  单 Target 串行、多 Target 并行 → 必须写清楚。
  不写 → 实现者猜 → 要么过度加锁，要么漏加锁。
```

**检查项：**
- [ ] 什么可以并行、什么必须串行
- [ ] 执行模型（单线程/异步/线程池）有明确假设吗
- [ ] 有没有共享状态需要锁

---

## 十、Review 方法论

### 22. 架构 Review 三轮

```
第一轮: 找模糊。每句话问"怎么做"。没有回答的就是模糊。
第二轮: 找冲突。同一个概念在两个地方的定义不一致。
第三轮: 找不合理。设计本身有问题（循环依赖、锁范围过窄...）
```

**检查项：**
- [ ] 每个 Section 能回答"怎么做"吗
- [ ] 同一个概念在所有 Section 的表述一致吗
- [ ] 数据流走一遍有没有循环/竞态/重复

### 23. 用外部 Reviewer

```
Embed Agent:
  Codex review 3 轮，发现 23 个问题。
  自己写 → 看不出自己文档的矛盾。
  换人/换模型读 → 新眼看到新问题。
```

**检查项：**
- [ ] 让没参与设计的人（或另一个 AI）读过吗
- [ ] reviewer 的每条反馈都处理了吗（修/记录不修的理由）
- [ ] 有争议的点单独讨论了吗

### 24. 不依赖已有代码

```
Embed Agent:
  先归档原型代码和旧文档。
  新架构从零设计，不反向约束。
  原型作为"可回收素材"而非"设计前提"。
```

**检查项：**
- [ ] 架构文档能不引用代码路径吗
- [ ] 如果旧代码不存在，这个架构还能成立吗
- [ ] 有没有"因为旧代码这样写所以架构这样画"
