# Artifact Validation Agent 场景库

> 状态：Draft  
> 日期：2026-04-28  
> 目的：用工程师能直接理解的话，整理嵌入式真机验证的常见场景。  
> 原则：场景库是参考手册，不是硬编码流程；不造概念，不写学术分类。

## 1. 一句话

Artifact Validation Agent 不是只会“刷机跑 smoke”。

场景库不是执行脚本。

它的作用是给 Task Planner 提供常见问题的工程经验：

```text
这种问题通常要把板子弄成什么状态，
通常要做什么动作，
通常要盯什么现象，
失败时通常要抓什么证据，
通常怎么判断过没过。
```

最终怎么编排，仍然由 Task Planner 根据需求、Target Profile、可用能力和约束生成 Plan。

Agent 要做的是：

```text
把产物放到真实板子上，
让板子进入要验证的状态，
做一件可能暴露问题的动作，
过程中盯住关键现象，
出问题时把现场抓全，
最后告诉 Coding Agent / Human：过了没、哪里不对、证据在哪。
```

## 2. 每个场景都按 8 个问题写

| 项 | 人话问题 |
|---|---|
| 准备 | 跑这个场景前要准备什么？要刷机、联网、插外设、开服务吗？ |
| 状态 | 开始验证时，板子应该处于什么状态？ |
| 动作 | Agent 要对板子做什么？ |
| 观察 | 过程中要盯什么现象？ |
| 证据 | 正常和失败时分别要抓什么？ |
| 判断 | 怎么算通过，怎么算失败？ |
| 恢复 | 跑完或跑挂后，怎么把板子恢复到可用状态？ |
| 风险 | 这个场景允许哪些危险动作？例如断电、重刷、杀进程、改网络。 |

这 8 个问题比“执行步骤”更重要。

原因是：LLM 可以自己组合能力，但它需要知道一个场景里哪些信息重要。

比如“网络断连恢复”不等于固定执行某几条命令。  
它真正提醒 Planner 的是：

```text
要能断网和恢复网络，
要观察服务是否重连，
要记录重连耗时，
要确保测试结束后网络恢复，
还要检查约束是否允许故障注入。
```

原因是嵌入式问题经常不是命令失败，而是：

```text
命令没报错，但设备已经重启了。
进程还在，但已经不响应了。
ADB 还连着，但屏幕黑了。
测试返回 pass，但日志里已经有 panic。
系统还在喂狗，但业务已经死了。
```

## 3. 场景总览

| 大类 | 常见问题 |
|---|---|
| 启动类 | 启动挂了、boot 循环重启、boot 时序问题、ADB 不回来 |
| 进程/服务类 | 进程 crash、死锁、IPC 不通、启动顺序错、假保活 |
| 黑卡死类 | 设备无响应、黑屏、串口静默但 ADB 还在、watchdog 没复位 |
| 通信/连接类 | 网络断连恢复、ADB 断连、通信超时、丢包、重连失败 |
| 资源类 | 内存泄漏、CPU 异常、存储满、fd 泄漏、日志风暴 |
| 故障注入类 | 断电恢复、OTA 中断、watchdog 触发、服务被 kill 后恢复 |
| 外设类 | 外设不响应、外设异常恢复、热插拔、总线卡住 |
| 电源/硬件类 | 低功耗唤醒、温度过高、电压波动、中断风暴 |
| 性能/稳定性类 | 响应变慢、长时间老化、系统逐渐不稳定 |
| 权限/配置/版本类 | 权限错误、配置损坏、数据迁移失败、版本不匹配 |

## 4. 启动类问题

### 4.1 启动挂了

| 项 | 内容 |
|---|---|
| 准备 | 准备 firmware 或系统镜像，确认允许刷机。 |
| 状态 | 板子刚刷完，准备启动。 |
| 动作 | 等它启动。 |
| 观察 | 串口有没有输出，有没有 panic，ADB 什么时候回来。 |
| 证据 | 串口全程日志、panic 位置、最后输出窗口、ADB 状态变化。 |
| 判断 | 启动完成且 ADB 回来就算过；出现 panic 或启动超时就算失败。 |
| 恢复 | 保存现场后尝试重启，必要时重新刷回稳定版本。 |
| 风险 | 允许刷机和重启；是否允许断电由 Human 配置。 |

### 4.2 Boot 循环重启

| 项 | 内容 |
|---|---|
| 准备 | 串口必须可用，最好能读取 reset reason。 |
| 状态 | 板子刚刷完或刚上电。 |
| 动作 | 观察它启动一段时间。 |
| 观察 | 是否不停重启，每次重启到哪一步，重启间隔是否固定。 |
| 证据 | 每次重启的串口日志、重启原因、boot count、最后成功阶段。 |
| 判断 | 应该稳定运行；短时间内多次重启就算失败。 |
| 恢复 | 保存所有重启片段后停止 run，避免无限循环刷坏设备或刷爆日志。 |
| 风险 | 允许等待和重启；不应无限重试。 |

### 4.3 Boot 时序问题

| 项 | 内容 |
|---|---|
| 准备 | 配置关键服务名和启动 marker。 |
| 状态 | 系统刚启动，多个服务要按顺序起来。 |
| 动作 | 等启动完成，同时记录服务启动顺序。 |
| 观察 | 每个服务什么时候启动，有没有依赖失败，有没有 timeout。 |
| 证据 | 服务启动时间线、依赖失败日志、init/systemd 日志、串口窗口。 |
| 判断 | 服务应该按预期顺序启动；依赖未准备好就启动导致失败，算失败。 |
| 恢复 | 保存启动时间线后重启或重刷。 |
| 风险 | 一般只观察，不做危险动作。 |

### 4.4 ADB 不回来

| 项 | 内容 |
|---|---|
| 准备 | 串口和 ADB 配置可用。 |
| 状态 | 板子正在启动或刚启动完成。 |
| 动作 | 等 ADB online。 |
| 观察 | 串口是否显示 boot 完成，ADB 是否一直 offline，USB 是否重枚举。 |
| 证据 | 串口 boot 日志、ADB 状态变化、USB/内核日志、最后输出窗口。 |
| 判断 | 在阈值内 ADB online 算过；boot 完成但 ADB 长时间不回来算失败或暂停。 |
| 恢复 | 先保存现场，再按策略重启 adb 服务、重启设备或让 Human 接管。 |
| 风险 | 是否允许重启设备由约束决定。 |

## 5. 进程/服务类问题

### 5.1 进程挂了

| 项 | 内容 |
|---|---|
| 准备 | 知道进程名、启动方式、日志位置。 |
| 状态 | 服务刚启动或运行中。 |
| 动作 | 观察服务行为，必要时拉起服务。 |
| 观察 | 进程是否突然退出，有没有 crash 日志，是否被系统拉起。 |
| 证据 | crash stack、core/tombstone、进程日志、dmesg/logcat、退出码。 |
| 判断 | 进程应该持续运行；异常退出或反复 crash 算失败。 |
| 恢复 | 抓完证据后按策略重启服务或重启设备。 |
| 风险 | 允许拉起或重启服务；是否允许 kill 进程需配置。 |

### 5.2 进程死锁/卡住

| 项 | 内容 |
|---|---|
| 准备 | 有能调用服务的测试命令或接口。 |
| 状态 | 服务正在跑。 |
| 动作 | 调用它、压测它或让它处理请求。 |
| 观察 | 请求是否响应，线程是否卡住，日志是否停止输出。 |
| 证据 | 线程栈、进程状态、锁信息、调用耗时、最后日志窗口。 |
| 判断 | 服务应该在阈值内响应；无响应或线程卡死算失败。 |
| 恢复 | 先 dump 线程栈，再重启服务或设备。 |
| 风险 | dump 和重启服务通常允许；强杀进程需配置。 |

### 5.3 进程间通讯不通

| 项 | 内容 |
|---|---|
| 准备 | 两个服务都能启动，有可重复调用的接口或测试脚本。 |
| 状态 | 两个服务都启动完成。 |
| 动作 | 让它们互相调用 1000 次，中途可重启其中一个服务。 |
| 观察 | 调用能不能成功，多久返回，有没有超时，服务是否 crash。 |
| 证据 | 每次调用耗时、错误率、两边日志、线程栈、dmesg/logcat。 |
| 判断 | 错误率不能超过阈值，服务必须自动恢复；超时或死锁算失败。 |
| 恢复 | 保存双方状态后重启服务，必要时重启设备。 |
| 风险 | 是否允许中途重启或 kill 服务要由场景明确写出。 |

### 5.4 进程启动时序问题

| 项 | 内容 |
|---|---|
| 准备 | 配置进程依赖关系、启动方式和 ready marker。 |
| 状态 | 多个进程需要按顺序启动。 |
| 动作 | 按指定顺序和间隔启动进程，或观察系统自动启动。 |
| 观察 | 每个进程什么时候启动，依赖是否已经 ready。 |
| 证据 | 启动时间线、依赖检查日志、服务状态、失败日志。 |
| 判断 | 依赖 ready 后再启动算过；依赖未 ready 导致失败算失败。 |
| 恢复 | 停止相关进程，恢复到干净状态再重跑。 |
| 风险 | 允许启动/停止服务；不默认允许重刷。 |

### 5.5 假保活

| 项 | 内容 |
|---|---|
| 准备 | 有业务心跳或健康检查接口。 |
| 状态 | 服务和系统都看起来在运行。 |
| 动作 | 长时间跑业务，同时周期性检查健康状态。 |
| 观察 | 进程是否还在，业务心跳是否还在，请求是否还能处理。 |
| 证据 | 健康检查结果、进程状态、业务日志、watchdog 喂狗记录。 |
| 判断 | 进程在但业务不响应，或系统仍喂狗但业务已死，算失败。 |
| 恢复 | 保存健康检查失败窗口，重启服务或设备。 |
| 风险 | 允许健康检查；是否允许触发 watchdog 需配置。 |

## 6. 黑卡死类问题

### 6.1 设备不动了

| 项 | 内容 |
|---|---|
| 准备 | 配置心跳、串口、ADB 或其他活性检查。 |
| 状态 | 设备正常运行中，测试程序在跑。 |
| 动作 | 压测或长时间运行，等它暴露问题。 |
| 观察 | 心跳是否还在，串口是否停止输出，ADB 是否能响应。 |
| 证据 | 最后串口窗口、dmesg、进程状态、心跳记录、重启原因。 |
| 判断 | 心跳没了但 watchdog 没复位，或者设备完全无响应，算失败。 |
| 恢复 | 先尽量保存现场；无响应时按策略 power cycle。 |
| 风险 | power cycle 是危险动作，必须配置允许。 |

### 6.2 黑屏

| 项 | 内容 |
|---|---|
| 准备 | 需要截图、拍屏、display 日志或 Surface 状态采集能力。 |
| 状态 | 设备在跑，屏幕应该有输出。 |
| 动作 | 观察屏幕，必要时注入输入事件。 |
| 观察 | 屏幕有没有输出，画面是否刷新，输入有没有反应。 |
| 证据 | 截图或拍屏、display 日志、input 日志、Surface 状态、logcat。 |
| 判断 | 屏幕应该有输出且能响应；黑屏或画面不刷新算失败。 |
| 恢复 | 抓证据后重启 UI 服务或重启设备。 |
| 风险 | 允许截图和输入注入；重启图形服务需配置。 |

### 6.3 串口没输出但 ADB 还在

| 项 | 内容 |
|---|---|
| 准备 | 串口和 ADB 都可用，知道设备是否可能进入 sleep。 |
| 状态 | 设备正常运行。 |
| 动作 | 同时观察串口和 ADB。 |
| 观察 | 串口是否停止输出，ADB 是否还能连，进程是否还在跑。 |
| 证据 | 最后串口窗口、ADB 状态、进程列表、系统电源状态。 |
| 判断 | 如果不是 sleep 且串口应有输出，长时间静默需要诊断；ADB 也不响应则失败。 |
| 恢复 | 尝试唤醒设备；失败则保存现场并暂停或重启。 |
| 风险 | 唤醒动作通常安全；重启需配置。 |

## 7. 通信/连接类问题

### 7.1 网络断连恢复

| 项 | 内容 |
|---|---|
| 准备 | 设备已联网，服务已连接到目标端。 |
| 状态 | 网络正常，服务正常连接。 |
| 动作 | 断网 30 秒再恢复。 |
| 观察 | 网络什么时候断，什么时候恢复，服务是否自动重连。 |
| 证据 | 网络状态变化日志、服务重连日志、重连耗时、错误码。 |
| 判断 | 网络恢复后在阈值内重连成功算过；不能重连或服务 crash 算失败。 |
| 恢复 | 确保网络恢复正常，必要时重启网络服务。 |
| 风险 | 允许改网络；不允许断电或重刷，除非明确配置。 |

### 7.2 ADB 断连

| 项 | 内容 |
|---|---|
| 准备 | ADB 连接正常，有串口作为旁路观察。 |
| 状态 | 设备 ADB 正常连接。 |
| 动作 | 长时间运行或压测。 |
| 观察 | ADB 会不会突然断，断之前设备状态是否异常。 |
| 证据 | ADB 状态变化、断连前串口窗口、USB 日志、dmesg/logcat。 |
| 判断 | ADB 应该稳定连接；非预期断连算失败或需要诊断。 |
| 恢复 | 尝试重新连接 ADB；失败则保存串口现场并暂停。 |
| 风险 | 重启 ADB 服务可配置；重启设备需配置。 |

### 7.3 通信超时/丢包

| 项 | 内容 |
|---|---|
| 准备 | 有可重复通信的测试脚本和阈值。 |
| 状态 | 设备正常通信。 |
| 动作 | 大量请求或长时间请求。 |
| 观察 | 有没有超时、丢包、响应延迟抖动。 |
| 证据 | 每次通信耗时、失败率、延迟分布、服务日志、网络日志。 |
| 判断 | 超时率、丢包率、延迟必须在阈值内；超过阈值算失败。 |
| 恢复 | 停止压测，恢复网络和服务状态。 |
| 风险 | 压测强度需要限制，避免影响共享环境。 |

## 8. 资源类问题

### 8.1 内存泄漏

| 项 | 内容 |
|---|---|
| 准备 | 配置采样间隔、目标进程、运行时长和泄漏阈值。 |
| 状态 | 设备正常运行。 |
| 动作 | 长时间跑业务或压测。 |
| 观察 | 内存是不是越来越多，哪个进程在涨，是否 OOM。 |
| 证据 | 周期性内存数据、进程内存分布、OOM 日志、测试负载记录。 |
| 判断 | 内存应稳定或在可接受范围内波动；持续增长超过阈值算失败。 |
| 恢复 | 停止负载，保存最后状态，必要时重启服务。 |
| 风险 | 长跑占用设备时间，需要 target lease。 |

### 8.2 CPU 占用异常

| 项 | 内容 |
|---|---|
| 准备 | 配置 CPU 阈值、采样间隔和目标进程。 |
| 状态 | 设备正常运行。 |
| 动作 | 跑业务或压测。 |
| 观察 | CPU 占用是否异常高，哪个进程或线程占用高。 |
| 证据 | CPU 曲线、进程 CPU 分布、线程 CPU 分布、负载记录。 |
| 判断 | CPU 应在合理范围；持续高于阈值或异常尖峰算失败。 |
| 恢复 | 停止压测，保存 CPU/线程状态。 |
| 风险 | 压测可能影响温度和稳定性，需要限制时长。 |

### 8.3 存储满

| 项 | 内容 |
|---|---|
| 准备 | 配置可写分区、写入量和安全上限。 |
| 状态 | 设备正常运行。 |
| 动作 | 长时间跑或模拟大量写入。 |
| 观察 | 存储空间是否越来越少，是否出现写失败。 |
| 证据 | 存储使用量曲线、写入日志、错误日志、分区状态。 |
| 判断 | 系统应该能处理空间不足；关键服务不能异常 crash。 |
| 恢复 | 清理测试文件，确认分区恢复。 |
| 风险 | 不能写满关键分区，除非场景明确允许。 |

### 8.4 fd 泄漏

| 项 | 内容 |
|---|---|
| 准备 | 配置目标进程、采样间隔和 fd 阈值。 |
| 状态 | 设备正常运行。 |
| 动作 | 长时间跑业务或反复建立连接。 |
| 观察 | 打开的 fd 数是否持续增长。 |
| 证据 | 周期性 fd 数、fd 列表、对应进程日志、错误日志。 |
| 判断 | fd 数应该稳定；持续增长超过阈值算失败。 |
| 恢复 | 停止负载，保存 fd 列表，重启服务。 |
| 风险 | 长跑占用设备时间。 |

### 8.5 日志风暴

| 项 | 内容 |
|---|---|
| 准备 | 配置日志采样和存储空间监控。 |
| 状态 | 设备正常运行。 |
| 动作 | 跑会触发大量日志的业务或压力。 |
| 观察 | 日志量是否异常大，CPU/IO 是否被日志拖垮，分区是否变满。 |
| 证据 | 日志速率、CPU/IO 曲线、存储曲线、异常模块名。 |
| 判断 | 日志量应在阈值内；日志打爆系统或分区算失败。 |
| 恢复 | 关闭负载，清理测试日志。 |
| 风险 | 不能刷爆关键分区。 |

## 9. 故障注入类问题

### 9.1 断电恢复

| 项 | 内容 |
|---|---|
| 准备 | 需要可控电源或继电器，确认允许断电。 |
| 状态 | 设备正常运行，最好正在执行关键业务。 |
| 动作 | 突然断电再上电。 |
| 观察 | 能不能正常启动，数据有没有丢，文件系统是否损坏。 |
| 证据 | 断电前状态、启动日志、数据完整性检查、文件系统状态。 |
| 判断 | 应能正常启动且关键数据完整；变砖或数据损坏算失败。 |
| 恢复 | 上电后检查系统状态，必要时重刷。 |
| 风险 | 高风险动作，必须 Human 明确允许。 |

### 9.2 OTA 升级中断

| 项 | 内容 |
|---|---|
| 准备 | 准备 OTA 包、旧版本、回滚检查方式。 |
| 状态 | 正在 OTA 升级。 |
| 动作 | 中途断电、断网或重启。 |
| 观察 | 能不能回滚，回滚后能不能正常启动，版本状态是否一致。 |
| 证据 | 升级日志、回滚日志、slot/版本状态、启动日志。 |
| 判断 | 应该能回滚或继续升级成功；变砖或版本状态混乱算失败。 |
| 恢复 | 回到稳定版本，清理失败升级状态。 |
| 风险 | 高风险，必须允许断电或重启。 |

### 9.3 看门狗触发

| 项 | 内容 |
|---|---|
| 准备 | 确认 watchdog 配置、重启原因读取方式。 |
| 状态 | 设备正常运行。 |
| 动作 | 让关键进程或系统路径卡住，触发 watchdog。 |
| 观察 | watchdog 是否触发，设备是否重启，重启后是否正常。 |
| 证据 | watchdog 日志、重启原因、重启前最后日志、重启后状态。 |
| 判断 | watchdog 应按预期触发并恢复系统；不触发或重启后异常算失败。 |
| 恢复 | 等设备恢复，确认服务正常。 |
| 风险 | 高风险，可能导致数据丢失，必须显式允许。 |

### 9.4 服务被 kill 后恢复

| 项 | 内容 |
|---|---|
| 准备 | 确认服务名和重启策略。 |
| 状态 | 服务正常运行。 |
| 动作 | kill 服务进程。 |
| 观察 | 服务是否被自动拉起，业务是否恢复，是否有连锁 crash。 |
| 证据 | kill 时间点、服务管理日志、业务恢复耗时、相关进程状态。 |
| 判断 | 服务应在阈值内恢复；不能恢复或拖死其他服务算失败。 |
| 恢复 | 确保服务恢复到正常状态。 |
| 风险 | 允许 kill 指定服务，不允许 kill 系统关键服务，除非明确配置。 |

## 10. 外设类问题

### 10.1 外设不响应

| 项 | 内容 |
|---|---|
| 准备 | 外设连接正常，有访问外设的测试命令。 |
| 状态 | 设备正常启动，外设应该工作。 |
| 动作 | 访问外设。 |
| 观察 | 外设有没有响应，总线有没有报错或卡住。 |
| 证据 | 外设日志、总线状态、驱动日志、错误码。 |
| 判断 | 外设应该响应；不响应或驱动报错算失败。 |
| 恢复 | 重试访问，必要时重置外设或重启驱动。 |
| 风险 | 重置外设需配置；不默认断电。 |

### 10.2 外设异常恢复

| 项 | 内容 |
|---|---|
| 准备 | 有办法让外设异常，例如断电、热插拔、模拟错误。 |
| 状态 | 外设正常工作。 |
| 动作 | 让外设异常，再恢复。 |
| 观察 | 驱动能不能恢复，设备能不能继续用。 |
| 证据 | 异常时日志、恢复过程日志、外设状态、驱动状态。 |
| 判断 | 外设恢复后应继续可用；驱动卡死或无法恢复算失败。 |
| 恢复 | 恢复外设连接和电源，确认状态正常。 |
| 风险 | 断外设电或热插拔必须配置允许。 |

### 10.3 外设热插拔

| 项 | 内容 |
|---|---|
| 准备 | 外设支持热插拔，测试夹具可控。 |
| 状态 | 外设已连接且工作正常。 |
| 动作 | 插拔外设一次或多次。 |
| 观察 | 系统是否识别插拔，驱动是否恢复，业务是否继续。 |
| 证据 | 内核日志、设备枚举日志、业务日志、错误码。 |
| 判断 | 插回后应恢复可用；驱动挂住或业务不恢复算失败。 |
| 恢复 | 确认外设重新连接并清理测试状态。 |
| 风险 | 反复插拔可能损伤硬件或夹具，需要限制次数。 |

## 14. Agent 怎么使用这篇场景库

Agent 不应该凭空“智能规划”。

它应该这样工作：

```text
收到需求
-> 找 1-3 个相关场景作为参考
-> 摘出场景里重要的观察、证据、判断和风险
-> 再结合 Target Profile、能力列表和 constraints
-> 由 Task Planner 生成 Plan
-> Orchestrator 校验 Plan
-> 能执行就执行，缺能力就明确告诉调用方缺什么
```

例子：

```text
需求：验证断网后服务能不能恢复。
匹配场景：网络断连恢复。
需要能力：改网络、观察服务连接状态、采服务日志。
如果 target 没有网络控制能力，Agent 不能假装能测，只能报告能力不足。
```

场景库不能直接驱动执行。

不能这样做：

```text
if 场景 == 网络断连恢复:
  固定执行 cut_network -> sleep -> restore_network
```

应该这样做：

```text
Task Planner 参考“网络断连恢复”的常见做法，
再根据这次需求和 target 能力生成具体 Plan。
```

## 15. 第一版优先做哪些场景

P0 不要一口吃完所有场景。

建议第一版只选这 6 个：

| 场景 | 为什么优先 |
|---|---|
| 启动挂了 | 最常见，最能体现 serial + ADB + evidence 的价值。 |
| ADB 不回来 | 真机验证高频问题，适合主动观察。 |
| 进程挂了 | 直接连接到 Coding Agent 的修复闭环。 |
| 进程间通讯不通 | 能体现“不是只跑命令”，需要观察延迟、错误率和恢复。 |
| 网络断连恢复 | 典型故障注入，风险可控。 |
| 设备不动了 | 能体现黑卡死和 evidence window 的价值。 |

暂时不做：

| 场景 | 为什么后做 |
|---|---|
| 断电恢复 | 需要电源控制，风险高。 |
| OTA 中断 | 容易变砖，恢复成本高。 |
| 外设异常恢复 | 依赖具体外设和夹具。 |
| 低功耗唤醒 | 需要更多硬件能力和长时间测试。 |
| 温度/电压 | 需要实验室设备和安全边界。 |
| 长时间老化 | 占用设备时间长，先有 target lease 再做。 |

## 16. 收口

这篇文档不是最终场景标准库。

它的作用是让团队先统一语言：

```text
不要说“跑个测试”。
要说清楚：
板子先要是什么状态，
Agent 要做什么动作，
过程中盯什么现象，
失败时抓什么证据，
最后怎么判断过没过，
跑完怎么恢复，
哪些危险动作被允许。
```

后续每遇到一个真实问题，就按这 8 项补进来。
