# Embed Agent 如何做成别人愿意用的产品

> 状态：Draft
> 日期：2026-04-28
> 目的：在已有产品定义、架构、功能和交互文档基础上，回答一个更现实的问题：`Embed Agent` 怎么设计，别人才愿意持续使用，甚至愿意付钱。

> 当前状态：背景参考。本文包含部分旧口径。当前正式口径以 [EMBED-AGENT-ROLE-MODEL.md](EMBED-AGENT-ROLE-MODEL.md)、[EMBED-AGENT-SCENARIOS-AND-CALLS.md](EMBED-AGENT-SCENARIOS-AND-CALLS.md)、[EMBED-AGENT-FUNCTION-LIST.md](EMBED-AGENT-FUNCTION-LIST.md) 和 [EMBED-AGENT-FIRST-SLICE.md](EMBED-AGENT-FIRST-SLICE.md) 为准。

## 1. 先说结论

别人不会因为我们“也有 agent”和“也能接 LLM”就买单。  
他们会因为这东西真的帮他们少掉了痛苦，才愿意迁移、愿意付费、愿意团队落地。

对 `Embed Agent` 来说，真正该卖的不是“AI 很聪明”，而是这四个结果：

- 更快进入一次真实设备验证
- 更少重复配置和重复劳动
- 更快抓到失败现场并进入下一轮修复
- 团队共享设备和经验时不再混乱

一句话：

```text
不是卖一个会聊天的 agent
而是卖一个会把嵌入式验证现场管顺的系统
```

再说直白一点：

```text
我们不是替代 Codex / Claude Code
我们是给它们补上真实设备现场、真实运行闭环和真实证据链
```

## 2. 别人为什么不用现有方案

用户今天已经有很多办法“勉强把事情做完”：

- 手写脚本
- 串口工具 + SSH + 刷机工具手工串起来
- pytest / Robot / labgrid / LAVA / tbot 这种局部方案
- Claude Code / Codex 这种通用 coding agent

这些方案不是没能力，而是有几个共同问题：

| 现状 | 用户真实痛点 |
|---|---|
| 工具很多 | 人要自己拼流程 |
| 自动化很多 | 但很难长期复用 |
| agent 能写代码 | 但不擅长管真实设备现场 |
| 有日志 | 但没有结构化证据交接 |
| 有设备 | 但共享后容易冲突 |
| 有经验 | 但沉淀不下来 |

所以机会不在“再做一个工具”，而在把这些碎片收成稳定闭环。

## 3. 我们现在手里真正有的东西

基于现有文档，`Embed Agent` 已经不是空概念了。我们手里有一套可以打的牌：

| 我们已有的方向 | 它的价值 |
|---|---|
| `Case / Run / Evidence / Verdict` 模型 | 不是只跑命令，而是能闭环 |
| `Target / Reservation / Connection / Power` | 不是只会连设备，而是能管理真实设备 |
| `Build / Delivery / Debug / Watch` | 不是只做分析，而是能真的执行 |
| `Evidence Package / Repair Handoff` | 不是只留下日志，而是能交接下一轮修复 |
| `Run Watch / Action Preview / Alert` | 不是黑盒自动化，而是人能接管 |
| `MCP + CLI` 双入口 | 不是只给人用，也不是只给 agent 用 |
| `Supervisor + Target Worker` 模型 | 不是单进程死扛多设备，也不是无总控乱多开 |

这套东西的关键优点是：

```text
我们管的是“真实现场 + 运行闭环 + 证据交接”
这正是通用 coding agent 最弱的一段
```

## 4. 我们真正的优势是什么

优势不能写成“我们也支持 LLM”。  
这没有任何壁垒。

更真实的优势应该写成下面这些：

### 4.1 我们离真实设备更近

外部 coding agent 擅长：

- 读代码
- 改代码
- 跑一些命令

但它们天然不擅长：

- 持续盯一块真实设备
- 管多通道连接
- 管设备占用和冲突
- 在出问题时保留现场
- 在失败后给出结构化交接物

这就是 `Embed Agent` 最核心的差异。

### 4.2 我们比自动化脚本更可复用

脚本的问题不是能不能跑，而是：

- 难共享
- 难升级
- 难理解
- 一换设备、一换协议、一换刷机方式就碎

如果我们把这些抽象成：

- profile
- preset
- override
- evidence package
- repair handoff

那它就从“脚本集合”变成了“可管理系统”。

### 4.3 我们比纯实验室工具更靠近修复闭环

labgrid、LAVA、tbot 这些很强，但它们更偏：

- 设备控制
- 验证编排
- 实验室管理

我们要补上的，是它们上面那一层：

```text
代码改动
-> 真实验证
-> 留证据
-> 交给 coding agent 继续修
```

这条桥搭起来了，产品就有了真正的独特性。

## 5. 什么叫“好用”

对这个产品，“好用”不是 UI 漂亮，也不是按钮多。

真正的“好用”至少有七个标准：

### 5.1 第一次可以重，第二次必须轻

第一次接项目时，可以允许用户补 profile。  
但第二次开始，系统必须尽量复用。

如果每次都要重填：

- 串口
- SSH
- 刷机方式
- 构建命令
- 协议参数
- 观察项

那产品就输给脚本了。

### 5.2 用户看到的是对象，不是工具

人应该围绕这些对象工作：

- case
- target
- run
- evidence
- verdict

而不是每天在：

- flash
- serial
- ssh
- grep
- reboot

之间反复跳。

### 5.3 长任务不能失明

一旦进入：

- 黑卡死
- 压测
- soak
- HIL

系统就必须给人一个最小盯盘面。  
否则用户心里没有安全感。

### 5.4 会改设备状态的动作必须可见

刷机、断电、reset、故障注入这些动作，一旦黑箱化，用户就不信任系统。

所以“好用”不只是省事，还包括：

- 看得见
- 能接管
- 有责任链

### 5.5 失败后不能让人重新拼现场

这是一个决定用户会不会留下来的关键点。

如果失败之后系统只给一大段原始日志，用户会觉得：

```text
这还是我自己来得快
```

必须给：

- failure snapshot
- evidence package
- verdict candidate
- next actions
- repair handoff

### 5.6 要有“记性”，但不能自作主张

用户喜欢系统记住：

- 常用板子
- 常用 recipe
- 常用构建和刷机方式

但不喜欢系统偷偷替他决定：

- 跑错设备
- 刷错镜像
- 沿用旧参数

所以好用的前提是：

```text
自动带出默认值
但运行前给出差异确认
```

### 5.7 要让人感觉是在增强自己，而不是替代自己

嵌入式工程师对“自动化替我做决定”天然敏感。  
好的体验不是把人踢出流程，而是：

- 重活系统做
- 危险动作人拍板
- 证据系统整理
- 修复人和 coding agent 一起推进

## 6. 什么才是真正卖得出去的点

不要卖“全能 agent”。  
那是一个会让用户立刻怀疑的表述。

更现实的卖点应该是下面这三条。

### 6.1 开发闭环提速

面向开发者，卖点不是 AI，而是：

```text
改完代码后，真机验证更快
失败后，下一轮修复更快
```

对应价值：

- 少手工配置
- 少来回切工具
- 少重复收日志

### 6.2 失败现场抓取

面向问题定位人员，卖点不是“自动化”，而是：

```text
黑屏、卡死、长时间异常时，更容易抓到现场
```

对应价值：

- 不容易丢关键日志
- 有物理恢复和故障快照
- 有 evidence package 可以交给别人继续处理

### 6.3 共享实验室秩序（后续阶段）

面向团队和实验室管理者，卖点不是“有 dashboard”，而是：

```text
多设备、多人、多 run 时不再混乱
```

对应价值：

- reservation
- target ownership
- action history / audit
- 共享知识和失败签名

## 7. LLM 在“好用”里到底该做什么

LLM 不是卖点本身，它应该成为“减少使用成本”的工具。

最适合的位置有这些：

| LLM 用法 | 真正改善什么 |
|---|---|
| case summary | 少写问题描述 |
| recipe suggestion | 少从零拼流程 |
| target suggestion | 少在多设备里瞎选 |
| log summary | 少自己翻爆量日志 |
| evidence summary | 少自己整理交接材料 |
| verdict candidate | 少自己先做一轮归纳 |
| similar case search | 少重复踩同一个坑 |
| profile drift warning | 少用旧配置误跑现场 |

不适合的位置也要写死：

- 不让 LLM 直接保管连接状态
- 不让 LLM 决定 run 状态
- 不让 LLM 直接批准高风险动作
- 不让 LLM 摘要替代原始证据

## 8. 第一版产品应该怎么卖

如果第一版什么都想卖，最后一定卖不动。

更合理的是做一个很聚焦的切入。

### 8.1 切开发者闭环

适合卖给：

- 有真实板子
- 经常改代码
- 经常要手工刷机和看日志

一句话卖点：

```text
把“改代码 -> 真机验证 -> 留证据 -> 下一轮修复”这条链打通
```

### 8.2 切专项问题定位

适合卖给：

- 黑屏 / 卡死 / 偶发异常多
- 失败现场经常抓不到

一句话卖点：

```text
让黑卡死、压测复线这种最烦的问题更容易抓现场
```

### 8.3 切共享实验室

适合卖给：

- 板子多
- 人多
- 设备经常冲突

一句话卖点：

```text
让设备共享、run 排队、证据归档有秩序
```

这三条里，第一版最建议先打第一条和第二条。  
第三条可以跟着长出来，但不要一开始就把自己卖成“大实验室平台”。

## 9. 第一版最重要的产品体验

如果让我只盯五件事，我会盯这五件：

| 体验 | 为什么关键 |
|---|---|
| profile / preset / override | 决定第二次是不是更轻 |
| run watch | 决定长任务是不是能放心交给系统 |
| action preview | 决定这次到底会不会改设备状态 |
| evidence package | 决定失败后是不是能快速进入下一轮 |
| repair handoff | 决定人和 coding agent 是不是真的形成闭环 |

这些做好了，用户会觉得这是产品。  
这些没做好，再多 adapter 也只是工具集合。

## 10. 暂时不要用来卖的东西

下面这些不要作为第一卖点：

- 我们也支持 LLM
- 我们也有 MCP
- 我们也能自动化
- 我们也能接很多工具
- 我们也想做平台

这些都太容易被替代，也太容易被用户理解成“又一个大而空的 AI 工具”。

## 11. 下一步最值得补的设计

从“能做什么”切到“别人愿意用什么”，我建议接下来补三份东西：

1. `Profile / Preset / Override` 对象模型  
   解决“别让我每次重配一遍”

2. `Run Watch / Action Preview / Alert` 交互草图  
   解决“长任务怎么盯、危险动作怎么拍板”

3. `Evidence Package / Repair Handoff` 模板  
   解决“失败之后怎么交给人或 coding agent 继续修”

这三件比继续扩 adapter 更重要。

## 12. 收口

别人愿不愿意用，不取决于我们有多少功能。  
取决于这东西是不是让他的真实工作变轻了。

对 `Embed Agent` 来说，真正应该追求的不是：

```text
我们是不是最全的 agent
```

而是：

```text
我们是不是最懂嵌入式验证现场
我们是不是最会记事
我们是不是最会留证据
我们是不是最会把下一轮修复接下去
```

如果这几点做到了，产品就有机会卖出去。  
如果没做到，接再多 LLM 也只是更贵的复杂度。
